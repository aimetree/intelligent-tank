# 协作流程

> 写给所有项目成员，尤其是新加入的合作者：这个项目怎么推进、东西放在哪里、两个人怎样在同一个 Project 里配合。
> 最近更新：2026-11-09

## 1. 一分钟了解

- **做什么**　产业科技智库与专业情报服务（业务A）：把科研、专利、企业、产品、政策、市场信息，做成有来源、可核验、可持续更新的知识与判断。首个方向是膜技术。
- **做到哪了**　阶段 0（基线与立项）已完成，准备进入阶段 1（可核验样品）。目前还没有客户、样品和软件。
- **怎么推进**　先样品、再试点、后产品化（D-16）；学术和企业两个方向都做（D-17）。计划不一次写完，在对话中逐步补充（D-18）。
- **谁在做**　两位成员加 Claude。成员提想法、做判断、批准；Claude 记录、整理、调研、起草，并维护文档和仓库。

## 2. 东西放在哪里

| 放什么 | 在哪里 | 怎么改 |
|---|---|---|
| 计划类文档：主页、决策、问题、清单、路线图、基线 | 本 Project 的文档，这里是正本 | 成员在对话里说，Claude 来改 |
| 文档的历史版本 | GitHub 仓库 `aimetree/intelligent-tank` 的 `docs/`，是快照 | Claude 在对话结束时同步；不在仓库里直接改 |
| 代码、数据、证据表 | GitHub 仓库，这里是正本 | 进入阶段 1 后开始产生 |
| 原始文件（交接包、Word 原件） | GitHub 仓库的 `archive/` | 只增不改 |

对话本身不是存放地。一场对话里说过的话，另一位成员和之后的对话都看不到；只有写进 Project 文档的内容才算数。重要的结论要让 Claude 记进文档。

## 3. 一条想法怎么变成做完的事

**提出 → 记入清单 → 批准 → 细化成任务卡 → 执行 → 记录结果 → 同步到仓库**

| 步骤 | 成员做什么 | Claude 做什么 | 落在哪里 |
|---|---|---|---|
| 1 提出 | 在任何一次对话里直接说 | 记成一条，写明提出人和日期，保留原话 | 《想法与补充清单》第 1 节 |
| 2 批准 | 说“批准 I-05、I-07”，或者“过一遍清单”逐条定 | 移入“已批准”；只需要点头的建议，直接记为决定 | 清单第 3 节；《决策记录》 |
| 3 细化 | 看任务卡，改到满意 | 写出目标、范围、产出、验收标准、前置条件 | 清单第 4 节 |
| 4 执行 | 做判断，提供专业核验和客户信息 | 调研、起草、整理数据、写代码 | 对应阶段的目录或仓库 |
| 5 记录 | 确认结论 | 更新决策、问题和主页上的状态 | 管理文档 |
| 6 同步 | 不用管 | 对话结束时把改动提交到仓库的 `main` | GitHub |

未批准的条目不动手做。Claude 不催批准，只在被问到或话题相关时提起清单里的条目。

## 4. 每次对话怎么开始和结束

- **开始**　在本 Project 里新开一个对话，第一句说清两件事：你是谁，这次想做什么。例如：“我是某某。先读项目主页和想法清单，然后……”
- **过程中**　想到新内容随时说。Claude 会区分哪些是你确认的决定，哪些只是它的建议。
- **结束**　这次对话如果改了文档，Claude 更新 Project 文档，并向 GitHub 提交一次；没有改动就不提交。

## 5. 两个人一起做时的规则

| 事项 | 规则 |
|---|---|
| 署名 | 每条想法、每个决定，都写明是谁提出或确认的 |
| 批准 | 目前由项目发起人批准。合作者是否有同样的批准权，待定（Q-23） |
| 避免互相覆盖 | Claude 改文档是整篇替换。两人同时在各自的对话里改同一份文档，后写的会盖掉先写的。所以同一时间只在一个对话里改管理文档；Claude 每次改之前都重新读取最新版 |
| 万一被覆盖 | GitHub 里留有每次同步的版本，可以对比和找回 |
| 意见不一致 | 两种意见都记进清单或《待决问题》，Claude 不代为决定 |
| GitHub 权限 | 每位成员需要对仓库有写权限，并在自己的 Claude 账号里连接 GitHub。没连上也能工作：文档照常更新，下一次有权限的对话会把仓库补齐 |

## 6. 必须遵守的约定

1. 事实、已定、建议、未知四类分开写；只有成员明确确认的才算已定。
2. 不编造客户、付款、价格、产品成熟度、验证结果、团队和排期。
3. 研究产出带出处：来源、日期、测试条件、适用范围、核验状态。
4. 对外的服务介绍不写实施计划、时间线、预算和公司战略框架；内部计划不受此限。
5. 文档里沿用脱敏写法（“某膜技术企业”“某研究人员”），除非成员决定改用真实名称。
6. 跨版本引用模块要带版本：“学术版 M07”和“通用版 M07”不是同一个模块。
7. 受版权限制的材料和客户的保密资料不进仓库。

完整版见《项目主页》第 4 节。

## 7. 整体路线

| 阶段 | 要回答的问题 | 状态 |
|---|---|---|
| 0 基线与立项 | 对项目的理解一致吗 | 已完成 |
| 1 可核验样品 | 相对客户自己用顶级 AI，我们多出来的是什么 | 下一步 |
| 2 付费试点 | 有人愿意付钱并再买吗 | 未开始 |
| 3 产品化 | 哪些部分重复发生，值得做成软件 | 未开始 |
| 4 正式上线 | 能对外稳定提供了吗 | 未开始 |
| 5 运营与运维 | 质量、成本、客户价值能持续吗 | 未开始 |

每个阶段都有过关条件，不过关不往下走。细节见《路线图_草案》。

## 8. 新成员第一次进来做什么

1. 读《项目主页》，了解当前状态和文档地图。
2. 读《项目基线_交接分析》，了解来龙去脉和已有方案。
3. 读《想法与补充清单》，看现在有哪些候选事项。
4. 确认自己能打开本 Project，对 GitHub 仓库有权限。
5. 开一个对话，说“我是某某，带我过一遍项目现状”，有想法直接提。
