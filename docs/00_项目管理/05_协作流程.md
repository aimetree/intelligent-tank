# 协作流程

> 写给所有项目成员，尤其是新加入的合作者：这个项目怎么推进、东西放在哪里、两个人怎样在同一个 Project 里配合。
> 最近更新：2026-11-11

## 1. 一分钟了解

- **做什么**　产业科技智库与专业情报服务（业务A）：把科研、专利、企业、产品、政策、市场信息，做成有来源、可核验、可持续更新的知识与判断。首个方向是膜技术。
- **做到哪了**　阶段 0（基线与立项）已完成，正在做阶段 1（可核验样品）的准备：Kai 2026-11-10 做完了两轮逐项判断（D-28 至 D-58），七项后续任务已批准（清单 T-03 至 T-09）。目前还没有客户、样品和软件。
- **怎么推进**　先样品、再试点、后产品化（D-16）；学术和企业两个方向都做（D-17）。两条都已由 Yu 和 Kai 确认。计划不一次写完，在对话中逐步补充（D-18）。
- **谁在做**　Kai、Yu 和 Claude。Kai 主要负责对整体项目的方案把关；Yu 主要负责代码、实现和开发相关的工作；Claude 记录、整理、调研、起草，并维护文档和仓库（D-23）。专业复核由 Kai 本人承担，也可以找他认识的人（D-52）；对接两位潜在对象的是 Kai（D-53）。Kai 和 Yu 共用同一个 Claude 账号，在同一个 Project 里工作。

## 2. 东西放在哪里

| 放什么 | 在哪里 | 怎么改 |
|---|---|---|
| 计划类文档：主页、决策、问题、清单、路线图、基线 | 本 Project 的文档，这里是正本 | 成员在对话里说，Claude 来改 |
| 文档的历史版本 | GitHub 仓库 `aimetree/intelligent-tank` 的 `docs/`，是快照 | Claude 在对话结束时同步；不在仓库里直接改 |
| 代码、数据、证据表 | GitHub 仓库，这里是正本 | 进入阶段 1 后开始产生 |
| 原始文件（交接包、Word 原件） | GitHub 仓库的 `archive/` | 只增不改 |

对话本身不是存放地。新开的对话不会带着之前对话的内容；两位成员虽然能在同一个账号里翻到对方的对话，但不应指望对方去翻。只有写进 Project 文档的内容才算数，重要的结论要让 Claude 记进文档。

## 3. 一条想法怎么变成做完的事

**提出 → 记入清单 → 批准 → 细化成任务卡 → 执行 → 记录结果 → 同步到仓库**

| 步骤 | 成员做什么 | Claude 做什么 | 落在哪里 |
|---|---|---|---|
| 1 提出 | 在任何一次对话里直接说 | 记成一条，写明提出人和日期，保留原话 | 《想法与补充清单》第 1 节 |
| 2 批准 | 说“批准 I-05、I-07”，或者“过一遍清单”逐条定。方案类条目要 Kai 批准才算数 | 移入“已批准”并写明批准人；只需要点头的建议，直接记为决定 | 清单第 3 节；《决策记录》 |
| 3 细化 | 看任务卡，改到满意 | 写出目标、范围、产出、验收标准、前置条件 | 清单第 4 节 |
| 4 执行 | 做判断，提供专业核验和客户信息 | 调研、起草、整理数据、写代码 | 对应阶段的目录或仓库 |
| 5 记录 | 确认结论 | 更新决策、问题和主页上的状态 | 管理文档 |
| 6 同步 | 不用管 | 对话结束时把改动提交到仓库的 `main` | GitHub |

未批准的条目不动手做。Claude 不催批准，只在被问到或话题相关时提起清单里的条目。

## 4. 每次对话怎么开始和结束

- **开始**　在本 Project 里新开一个对话，第一句说清两件事：你是谁，这次想做什么。例如：“我是 Kai。先读项目主页和想法清单，然后……”两人共用一个账号，Claude 分不出是谁在说话，所以这一句不能省。
- **过程中**　想到新内容随时说。Claude 会区分哪些是你确认的决定，哪些只是它的建议。需要你做选择时，Claude 用可点选的问题逐条给出（D-27）。Kai 不读长文件：给 Kai 的分析写进题目里，文件只作存档或交给 Yu。
- **结束**　这次对话如果改了文档，Claude 更新 Project 文档，并向 GitHub 提交一次；没有改动就不提交。

## 5. 两个人一起做时的规则

| 事项 | 规则 |
|---|---|
| 署名 | 每条想法、每个决定，都写明是 Kai 还是 Yu 提出或确认的。因为共用账号，只能靠对话里自报 |
| 批准 | 方案、方向和对外材料一类的条目，须经 Kai 确认才算已定；代码与实现类由 Yu 负责（D-24）。Yu 提出或同意的方案类条目，先记为“待 Kai 确认”，在清单第 2 节单独列出 |
| 避免互相覆盖 | Claude 改文档是整篇替换。两人同时在各自的对话里改同一份文档，后写的会盖掉先写的。所以同一时间只在一个对话里改管理文档；Claude 每次改之前都重新读取最新版 |
| 万一被覆盖 | GitHub 里留有每次同步的版本，可以对比和找回 |
| 意见不一致 | 两种意见都记进清单或《待决问题》，Claude 不代为决定 |
| GitHub | 两人共用同一个 Claude 账号，GitHub 连接是同一个，已经接通，不需要各自设置。新对话里由 Claude 自己接入仓库 |
| 共用账号 | 用量额度是两人共用的；Claude 分不出对话者。账号使用方式见《待决问题》Q-24：Kai 2026-11-10 定为维持现状（D-55） |

## 6. 必须遵守的约定

1. 事实、已定、建议、未知四类分开写；只有成员明确确认的才算已定。
2. 不编造客户、付款、价格、产品成熟度、验证结果、团队和排期。
3. 研究产出带出处：来源、日期、测试条件、适用范围、核验状态。
4. 对外的服务介绍不写实施计划、时间线、预算和公司战略框架；内部计划不受此限。
5. 文档里沿用脱敏写法（“某膜技术企业”“某研究人员”），除非成员决定改用真实名称。
6. 跨版本引用模块要带版本：“学术版 M07”和“通用版 M07”不是同一个模块。
7. 受版权限制的材料和客户的保密资料不进仓库。
8. 来源使用规则（D-56）：产出只用我们自己的总结、自己画的图表和带出处的事实数值；只用合法能看到的版本；条款明确禁止自动抓取或用于 AI 的来源改由人来读；每个来源登记许可情况和处理方式。
9. 现阶段只提供信息（D-60）：产出做到整理和描述两层，陈述数据说了什么，不写评价和建议。

完整版见《项目主页》第 4 节。

## 8. 新成员第一次进来做什么

1. 读《项目主页》，了解当前状态和文档地图。
2. 读《项目基线_交接分析》，了解来龙去脉和已有方案。
3. 读《想法与补充清单》，看现在有哪些候选事项。
4. 用同一个账号进入本 Project 即可；GitHub 已经接通，不需要额外设置。
5. 开一个对话，说“我是 Kai，带我过一遍项目现状”，有想法直接提。
6. Kai 负责方案把关，进来后先看清单第 2 节（待确认与候选事项）和第 4 节（任务卡）。需要背景时，看《全盘判断记录》、《项目基线》第 9 节的接手评估和《路线图_草案》。
