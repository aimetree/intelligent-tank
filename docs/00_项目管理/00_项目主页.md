> 产业科技智库与专业情报服务（业务A）的工作空间：计划、开发、上线、运维都在这里推进。

> 最近更新：2026-11-10

## 1. 项目是什么

把科研、技术、产品、竞争、政策、市场、工程应用和产业资源，组织成**有来源、可核验、可持续更新**的专业知识、数据与研究判断，为技术密集型行业的研发团队、企业和科研机构提供情报服务与产品。

- 业务A独立于另外两块业务：B（数字孪生）、C（智能运营）。
- 首个行业方向是膜技术（气体分离膜、离子传输与电化学膜）；体系要求能迁移到其他行业和客户。
- 品牌与产品名未定，“Intelligent Tank”是当前工作名。

## 4. 协作约定

1. **四类信息分开写**　事实（资料或查证可证）、已定（用户明确确认）、建议（助手判断，未确认）、未知。只有确认过的才进入“已定”。
2. **不编造**　客户付款、产品成熟度、软件完成度、独立验证结果、价格、团队、排期，一律不虚构。
3. **研究产出带出处**　每条关键数据保留：原始来源、发布日期、取得或核验时间、出处位置、单位、测试条件、适用范围、版本、许可、核验状态。
4. **对内与对外分开**　本 Project 内的计划可以有阶段和排期；对外服务介绍遵守已定要求，不含实施计划、时间线、团队预算、公司战略框架（D-07，假设 A-01）。
5. **脱敏**　沿用交接包的写法（“某膜技术企业”“某研究人员”“某研究机构”），直到用户决定在这里使用真实名称（A-03）。
6. **表达形式**　模块化、表格、矩阵、结构图优先；对外交付给完整文件（D-12）。
7. **跨版本引用模块必须带版本**　例如“学术版 M07”“通用版 M07”，两者不是同一个模块（D-08）。
8. **文档维护**　决策有变先改《决策记录》；问题关闭后在《待决问题》标注并把结论写入决策；归档资料不改写；重要变更在本页“更新记录”留一行。
9. **Project 与 GitHub 的分工**　计划类文档以 Project 为准；某次对话改了文档，就在结束时把它们单向同步到仓库 `aimetree/intelligent-tank` 的 `docs/`（提交前先拉取 main 的最新版本；管理类文档整份导出，归档资料只在新增时导出，仓库里缺的文档一并补上），不在仓库里直接改。代码、数据和原始文件以仓库为准，Project 里只放说明与结论（D-19）。新对话里需要先接入该仓库才能同步。同步时直接提交到 main，不走分支和合并请求（D-21）。
10. **想法先入清单**　新的更新或补充先记入《想法与补充清单》，保留用户原话；由用户批准后才细化成任务。未批准的不动手做，也不催批准（D-20）。
11. **两人协作**　项目由两位成员共同完成，两人共用同一个 Claude 账号（D-22），Claude 无法分辨对话者：对话开头不清楚是 Kai 还是 Yu 时先问。Kai 主要负责方案把关，Yu 主要负责代码与实现（D-23）。文档中的“用户”指项目成员；每条想法和决定都写明提出人或确认人，谁在对话中批准就记谁。改任何文档之前重新读取最新版，同一时间只在一个对话里改管理文档。成员意见不一致时两种都记录，不代为决定。方案、方向和对外材料一类的条目须经 Kai 确认才算已定，代码与实现类由 Yu 负责；Yu 提出或同意的方案类条目先记为“待 Kai 确认”，并列入清单第 2.0 节（D-24）。给成员看的说明在《协作流程》。
12. **用可点选的形式提问**　需要成员确认、选择或判断时，用可点选的提问逐条给出，每题自带必要背景（D-27）。
