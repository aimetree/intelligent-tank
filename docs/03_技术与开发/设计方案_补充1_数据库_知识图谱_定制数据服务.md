## 2. 系统框架与可迁移性（待编-25）

### 2.1 Kai 的话和已有的决定

Kai 2026-11-14 伦敦时间 17:29 的原话：“所以你要考虑 我们实际做的是一个系统框架 已膜为case，做出来的产品我们之后要方便迁移到其他的场景和研究领域”。其中“已”按“以”理解。

这和已定的两条一致：四层结构（D-02）；体系须跨行业、跨客户可迁移，不做成单一客户方案（D-03）。同一天 Kai 还定了业务范围先留在膜，只扩客户群（待编-16）。合起来：现在只做膜，但每一样东西都按“换个领域只换领域包”来做。上传的方案也是这个思路：通用数据模型加领域扩展，第一个领域只是案例，不是永久的边界（上传的方案 1.2、7.2）。

### 2.4 框架里现在带着“膜”字的地方

通用层里有几处是照膜写的。不影响现在做样品，换领域之前要改成中性的说法。建议，怎么改由 Yu 定：

| 在哪 | 现在的写法 | 换领域时的问题 |
|---|---|---|
| 《字段规格》v0.2 3.4 样品登记、2.2 枚举 | “这个来源里出现的每一张膜一项”；`baseline_form`（基准膜的形态）的取值是原样、预处理过、重铸、原文没写 | 别的领域的样品不是膜，基准的形态也不是这几种 |
| 《字段规格》v0.2 3.1 题目卡、2.2 枚举 | 分类维度的 `applies_to` 只能取 `membrane`（每一张膜）或 `material_class`（材料族） | 取值要能由题目卡定义 |
| 层级 | 材料、器件、系统三层（D-10） | 对能源材料大体通用；换到别的领域要重看 |
| 报告 skill v0.2 | 例句和标记表用的是膜的例子，如“同文基准膜” | 规则不变，例子要换 |

### 2.5 一个例子：换到催化剂数据要变什么

只是说明框架怎么迁，不是要做。上传的方案举过一个例子：两个催化剂都报告了 ORR 半波电位，但参比电极、换算方式、实验环境或测试协议不一致时，不能只按数值排名（上传的方案 6.2）。放进我们的框架：参比电极、换算方式、测试协议是指标字典里的条件项；“关键条件相同才并排”是可比规则；通行的基准样品是什么由懂行的人定。数据对象、流程、脚本和页面都不用动。

### 2.6 怎么知道迁得顺不顺

《路线图》阶段 3 的过关条件是第二个客户靠配置上线、不重建，并看复用率和配置工时；指标里有“复制”一组。上传的方案也把“通用技术组件在新项目中的复用程度”列为指标（13.3）。建议：从第二个题目起，每换一个题目记一笔配置工时和新增了哪些规则。企业样品（题目另定，D-50）是第一次检验；定制数据服务的每个项目也都记。

## 3. 数据库（待编-22）

### 3.1 定位

数据库是证据库长大之后的样子，不是另起一套。它有三个用处，前两个是已定的（D-131）：我们内部审核，确保信息真实可靠；给用户的信息源头；以后对客户开放，成为“给客户看的看板和数据库”和数据接口（D-41、D-45）。前期照现在的做法用数据文件演示，后期才建自己的数据库（D-133）。

### 3.2 数据模型的对照

上传的方案第 6.1 节列了 15 类实体。对照《字段规格》v0.2：10 类对得上，4 类有一部分，1 类没有。

| 上传的方案的实体 | 我们现在的对应 | 差在哪 |
|---|---|---|
| Source；Publication Metadata | 来源：题名、作者、标识、版本、取得途径、许可、处理方式 | 没有差。我们多了专利、政策法规、标准、资助记录的著录项目和状态 |
| Material | 实体里的“材料与技术类别”，加题目卡定的分类维度 | 有一部分：我们只到材料族，不记每种材料的组成和属性 |
| Sample / Formulation | 来源文件里的样品登记：原文样品名、角色、所属材料族、分类 | 对得上。跨来源出现的样品才另建样品实体 |
| Synthesis Process | 没有，只有“膜的预处理”一个可选条件 | 缺 |
| Characterisation | 厚度、电导率、渗透率这类性质记成材料层的指标 | 有一部分：结构和形貌的表征没有 |
| Experiment | 证据上的“同批测试标签”把同一套装置、同一套条件的一批数据串起来 | 有一部分：信息在，没有单独的对象 |
| Test Conditions | 证据的条件，条件项在指标字典里定义，必填的不能空 | 没有差 |
| Measurement；Performance Result | 证据：原文数值和单位、标准单位下的值、范围、误差、样本数、取得方式 | 没有差 |
| Application | 实体里的“应用与项目” | 没有差 |
| Evidence Record | 证据的出处位置、原文片段、图上读数记录、两遍抽取 | 没有差 |
| Quality & Review | 核验状态六档、风险档、机器核对结果、复核单 | 没有差，我们更细 |
| Relationship | 关系 16 种，都是“谁和谁有关”，每条带出处或标明推断 | 有一部分：没有材料、制备、结构、性能之间的关系，见第 4 节 |
| Version & License | 记录版本、数据版本、变化记录；来源的许可类别和处理方式 | 没有差 |

上传的方案 6.2 要求从一开始就保留的七样（原始和标准化的记录与单位；测试条件；来源证据和图表位置；缺失、推算和实测的区别；审核状态和修订历史；指标定义和可比条件），我们都已经有（《字段规格》v0.2 3.6；D-33、D-34、D-71、D-72）。

缺的三样（制备、结构表征、单独的实验对象）留到产品化阶段再加（待编-22、待编-23）。现在的题目卡十个问题不问制备和结构，试做不加。

### 3.3 分阶段

| 阶段 | 证据库是什么 | 从上传的方案并进来的 |
|---|---|---|
| 阶段 1 样品（现在） | 仓库里的数据文件，每个题目一套（D-30） | 不新增开发。留三个口子：实体、样品、关系都有稳定的编号（已有）；原文值和标准值都留（已有）；脚本里取数的函数按“查、比、取证据、看关联”四类来分（建议，Yu 定） |
| 阶段 2 试点 | 同上，按周期追加 | 定制数据服务的每个项目一套数据文件，和公共的分开存（D-39、设计方案原则 9） |
| 阶段 3 产品化 | 自己的数据库（D-133） | 关系数据库、后端接口、可复用的前端组件起步；图数据库、向量检索、Agent 编排等有了实际需求再加。抽取入库和用户查询分成两条流程。通用数据模型加领域扩展。统一接口，页面不直接依赖表结构。公开数据和客户私有数据分开。给 LLM 留结构化的工具接口，先当普通接口实现（上传的方案 7.2） |
| 以后 | 对客户开放的数据库和数据接口 | 功能见 3.5；数据接口的四个启动条件不变（D-45） |

### 3.4 后期的分层

上传的方案 7.1 把技术分成八层。对到我们现在有的和后期要有的（后期一栏与《设计方案》v0.2 第 10 章一致）：

| 层 | 我们现在（样品阶段） | 后期（产品化） |
|---|---|---|
| 数据来源 | 论文、商业膜资料、六类非学术来源，逐个登记许可（D-56、D-95） | 自动抓取为主，保留上传（D-133）；能抓哪些先问律师（D-57） |
| 抽取 | Claude 按模板抽两遍，脚本比对 | 采集与更新的流水线 |
| 核验 | 机器核对、人工核对、专业复核、复核单（D-33、D-80） | 核验的工作流和界面 |
| 核心数据 | 数据文件，十类对象（D-49） | 数据库，统一的对象与关系；两张图 |
| 服务与接口 | 没有，脚本直接读文件 | 查询、筛选、比较、访问控制的接口；以后是数据接口（D-45） |
| 应用 | 只读看板五页；报告（D-111、D-46） | 可登录的看板；给客户看的数据库；半自动出报告 |
| 用户与商务 | 没有账号 | 账号、收藏、套餐、项目咨询 |
| 治理 | 许可登记；可见范围；公共与专属分开存 | 权限、审计、客户数据隔离、合规审查 |

### 3.5 给客户看的数据库有哪些功能

上传的方案 4.1.1 给它的数据库 MVP 列了九项能力。作为“给客户看的看板和数据库”（D-41 的第三种服务形态）的功能候选：
